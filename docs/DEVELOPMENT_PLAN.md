# 墨页开发路线与任务拆分

> 版本：0.1.0 · 日期：2026-10-27 · 状态：MVP 已完成并在 Linux 上完成运行、E2E 与打包验证

## 1. 目标与范围

### 产品目标

为 Markdown 写作者提供一个安静、专注的桌面编辑环境：

- 一次只处理一个 Markdown 文件；
- 用 Vditor IR 模式在单屏内完成「写作 + 即时预览」；
- 不需要手动频繁保存，但关键操作前不能丢内容；
- 视觉上简洁、有纸张感，而不是把网页编辑器塞进 Electron。

### MVP 范围

| 包含 | 不包含（后续再考虑） |
| --- | --- |
| 打开单个本地 Markdown 文件 | 多标签、文件树、多文件工作区 |
| 单屏 Vditor IR 编辑与预览 | 分栏预览模式 |
| 编辑后 700ms 自动保存 | 云端同步 / 协作 |
| `Ctrl/Cmd + O` 打开、`Ctrl/Cmd + S` 保存 | 新建未命名文档、另存为 |
| 切换文档前保存、关窗前同步落盘 | 自动更新、签名发布 |
| 字数 / 字符 / 行数统计 | 导出 PDF / HTML |
| 无边框窗口与自绘控制栏 | 系统主题跟随 |
| Linux 打包验证与端到端测试 | Windows / macOS 实机验证 |

## 2. 技术路线

### 2.1 架构原则

前后端分离，但不引入不必要的 HTTP 服务：

```
渲染器（独立前端） ← contextBridge → 预加载桥 → 主进程（Electron 后端） → 本地 fs
```

- **前端**：React 19 + Vditor 3.11.3（IR） + 自研视觉层与保存状态机，只负责交互、渲染和状态展示。
- **后端**：Electron main 负责窗口、系统文件对话框、活动文档会话、原子写入与标题管理。
- **契约层**：`src/shared/desktop-api.ts` 同时被 Node 与 DOM TypeScript 工程引用，保证 IPC 两端类型一致。
- **安全边界**：preload 只暴露窄接口；渲染器没有 Node、没有任意路径读写，只能操作主进程当前打开的文件。

### 2.2 为什么选择 Vditor IR

- IR（即时渲染）满足「单屏同时编辑与预览」的核心体验。
- 内置 Markdown 快捷键、表格、任务列表、代码高亮与工具栏，减少重复造轮子。
- 通过本地资源目录离线运行，避免 CDN 依赖。
- 需要按 Vditor 的实际 DOM 结构做 CSS 深度定制，UI 才不会被默认样式拖累。

### 2.3 保存链路

自动保存不是简单地在 `input` 里调用 `writeFile`：

1. 输入事件触发后只标记 dirty 并启动 700ms 防抖；
2. 真正保存时从 Vditor `getValue()` 读取实时值，避免其内部回调延迟导致丢最后一段输入；
3. 主进程用 `sessionId` 绑定文档会话，旧会话的保存请求被拒绝；
4. 写入采用同目录临时文件 + `fsync` + `rename`，并恢复原权限；
5. 切换文件之前等待当前保存完成；失败则阻止切换；
6. 窗口 `beforeunload` 使用 `sendSync` 刷盘，确保关闭前最后一次输入落盘。

### 并行开发方式

1. 先冻结 `src/shared/desktop-api.ts`，让前端与后端在同一个类型契约上独立工作。
2. 后端任务只修改 `src/main` 与 `src/preload`；前端任务只修改 `src/renderer` 与样式。
3. 文件所有权保持互斥，避免并行开发产生冲突。
4. 主线程负责集成、运行验证、视觉验收、文档和 Git 提交。
5. 后端子任务独立验证了窗口、文件会话、BOM、权限、超大文件、stale session、flush 等行为；
   随后合并进主分支进行 UI 联调。

## 5. 关键决策与取舍

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 用 Electron main 持有文档会话，而不是前端传路径 | 防止渲染器任意文件写入；防 stale save 覆盖新文件 | 主进程状态需与 UI 同步 |
| 保存采用同步写 | 保证 `beforeunload` 的 `sendSync` 刷盘不与异步写竞争；Markdown 文件通常很小 | 大文件写入期间主进程事件循环短暂阻塞（限 20 MiB） |
| 保存前从 Vditor `getValue()` 读取 | 修复输入回调滞后导致最后一键丢失 | 每次保存增加一次 DOM→Markdown 转换 |
| 自绘标题栏 | 视觉统一、品牌感强 | 需要自行处理拖拽、窗口控制与平台差异 |
| 内置 Noto Serif SC 可变字体 | 中文衬线效果一致，不依赖用户系统字体 | 约 6 MB 字体资源 |
| Vditor 全套资源离线打包 | 无需网络、开发和打包行为稳定 | 应用体积增加约 24 MB |
| CSP 允许 inline 事件处理器但不允许 inline `<script>` | Vditor 的复制/图片预览按钮依赖 inline handler；同时阻止内联脚本注入 | 需要在文档中明确安全边界 |
| 仅实现单文件 | 聚焦核心书写体验，减少状态复杂度 | 无标签页/文件树/另存为 |

## 8. Git 协作约定

本仓库采用可回溯的小步提交，按职责拆分：

1. 脚手架：构建、依赖、共享 IPC 契约；
2. 后端：main + preload + 文件会话；
3. 前端：renderer + 视觉 + 自动保存；
4. 质量与文档：测试、示例、图标、README、路线与许可证。

开发过程中不提交 `node_modules`、`out`、`release`、生成的 Vditor 资源或临时调试脚本。
